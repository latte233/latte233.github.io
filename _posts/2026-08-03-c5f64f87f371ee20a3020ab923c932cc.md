## 本期速览

本期最大的事件是 **Agent Harness 的组织化转向**。Y Combinator 在 7 月 31 日亲自下场开源了内部用了大半年的多人协作 Agent 系统 [qm](https://github.com/yc-software/qm)，48 小时内 Hacker News 623 分、GitHub 突破 7000 Star，一个新词「Multiplayer Agent」随之出现。它的意义不在于代码本身，而在于它把 Agent 从「每人一个私人助理」重新定义为「整个组织共享一套带权限隔离的 Agent 基础设施」——这是 Agent 基础设施化的一个明确拐点，建议团队本周就安排验证。

第二条值得立即行动的信号是阿里开源的 [Open Code Review](https://github.com/alibaba/open-code-review)。这不是一个 demo 级项目，而是阿里内部服务了两年、覆盖数万开发者、检出过百万级缺陷之后才对外开源的生产级工具，Star 已达 17871，近 7 天 61 次 commit，8 月 2 日刚发 v1.8.5。它采用「确定性工程 + LLM Agent」的混合架构，规避了纯 LLM 代码审查噪音大的通病，对国内团队来说是本期落地成本最低、收益最直接的一条信号。

监管侧，**EU AI Act 的 GPAI 执法权已于昨日（8 月 2 日）正式生效**，AI Office 可以审计通用目的模型、要求整改并处以最高全球营业额 3% 或 1500 万欧元的罚款。同时 Article 50 透明度义务同步生效，而高风险场景义务则通过 Digital Omnibus 推迟到 2027-2028。这条信号从上期的 Trial 升级为 Adopt——它已经不是「将要发生」，而是「已经生效」的合规现实。

开源政策方面出现了一个重要的生态分裂信号：由 NVIDIA 黄仁勋牵头、微软和 Meta 联署的《Open Weights and American AI Leadership》公开信，签署方在一周内从 25 家增长到 230 家以上，但 OpenAI 和 Anthropic 的缺席使得「开放权重阵营 vs 闭源前沿阵营」的分野第一次被摆到了台面上。

微软研究院的 [SkillOpt](https://github.com/microsoft/SkillOpt) 提出把 Agent Skill 当作「可训练参数」来优化，在 6 个 benchmark、7 个模型、3 种 harness 共 52 个评测格上全部取得最优或持平，为 Skill 工程从手工编写走向系统性优化提供了方法论基础，值得关注。

## 重点信号详解

### qm（Y Combinator 多人协作 Agent Harness）

**象限**：Frameworks & Infrastructure
**环位**：Trial
**跨源热度分**：2.75

**是什么**：Y Combinator 在 7 月 31 日开源的多人协作 Agent Harness，项目名取自 quartermaster（军需官）。它给每位员工一个带作用域隔离的私有工作空间（独立记忆、文件、密钥串、权限、定时任务和持久化沙箱），同时允许整个团队在 Slack 频道、群聊和共享项目中与同一套 Agent 协作。

**为什么重要**：过去两年所有主流 Agent Harness 的心智模型都是「一个开发者、一台机器、一个 Agent」。qm 第一次把 Agent 当作组织级基础设施来设计，引入了权限作用域和多租户隔离这两个企业软件的核心概念。「Multiplayer Agent」这个词在发布后迅速传播，说明它击中了一个真实且普遍的痛点——当团队里有 50 个 Agent 在跑时，单人模型彻底失效。对企业内部平台团队而言，这可能是未来一年 Agent 基础设施的参考架构。

**当前状态**：MIT 协议，7164 Star（发布 4 天），48 小时内在 Hacker News 获得 623 分和 143 条评论。已发布 v0.1.4，近 7 天 40 次 commit，支持 Claude Code / Codex / OpenCode 多引擎切换，提供 Slack 和 Web 双端接入。当前仅 3 位贡献者，91 个未关闭 Issue，版本号仍在 0.1.x，说明 API 尚未稳定。

**建议下一步**：本周安排 1-2 人做 2 天 PoC，重点验证三件事——Slack 接入的实际协作体验、权限作用域隔离是否真的可靠、以及自托管部署的资源开销。鉴于其 0.1.x 的版本状态，建议先在非核心项目上试点，暂不接入生产代码仓库。

### Open Code Review（阿里开源 AI 代码审查）

**象限**：Tools & Products
**环位**：Trial
**跨源热度分**：2.6

**是什么**：阿里巴巴开源的 AI 代码审查 CLI 工具，命令名为 ocr。它读取 Git diff，通过具备工具调用能力的 Agent 将变更发送至可配置的 LLM，生成行级精度的结构化审查意见。Agent 可以读取完整文件、搜索代码库、检查其他变更文件来获取上下文，而不只是看 diff 表面。

**为什么重要**：AI 代码审查的最大问题一直是噪音——纯 LLM 方案容易产生大量无关或错误的意见，导致开发者很快就忽略它。Open Code Review 的混合架构针对性地解决了这一点：用确定性程序处理文件选择、变更分组和规则匹配这些不需要智能的环节，只把真正需要理解的部分交给 Agent。这个设计思路本身对任何做 AI 工程化的团队都有参考价值。对国内团队还有一个额外优势——支持私有化部署，代码不出域。

**当前状态**：Apache-2.0 协议，17871 Star，96 位贡献者，近 7 天 61 次 commit，8 月 2 日发布 v1.8.5。阿里内部已运行两年，服务数万开发者，累计检出百万级缺陷。内置 NPE、SQL 注入等安全规则。支持 CLI 本地使用、GitHub Actions 集成和多平台部署。除 diff 审查外，ocr scan 命令可审查整个文件，适合审计陌生代码库。

**建议下一步**：这是本期落地成本最低的信号，建议直接在一个中等规模的仓库上接入 GitHub Actions 试跑两周，统计有效意见率和误报率。如果有数据不出域的合规要求，重点验证私有化部署配合内部模型端点的效果。

### EU AI Act GPAI 执法权正式生效

**象限**：Practices & Ecosystem
**环位**：Adopt
**跨源热度分**：2.5

**是什么**：2026 年 8 月 2 日，欧盟 AI 法案针对通用目的 AI（GPAI）的完整执法权正式激活。欧盟 AI Office 从这一天起可以审计 GPAI 模型、要求提供方整改，并处以最高全球营业额 3% 或 1500 万欧元（取较高者）的罚款。同日生效的还有 Article 50 透明度义务。

**为什么重要**：这条信号本期从 Trial 升级为 Adopt，原因很简单——它已经不是预告而是现实。需要特别注意的是执法范围的分化：通过 Digital Omnibus 修订，高风险 AI 应用场景的义务被推迟到 2027 年 12 月和 2028 年，但透明度章节和 GPAI 执法机制保持原定时间表不变。这意味着如果业务涉及向欧盟市场提供或集成通用目的模型，合规窗口已经关闭；而如果是高风险应用场景，还有一年以上的准备时间。另一个实际影响是，GPAI 行为准则（Code of Practice）的签署与否，把模型供应商市场切分成了两个阵营，这已经成为一个可用于采购决策的信号。

**当前状态**：法规已生效，AI Office 具备完整审计和处罚权限。Article 99 和 Article 101 规定了具体罚则。市场上已出现针对 GPAI 提供方和 API 集成方的合规检查清单。

**建议下一步**：如果产品有欧盟用户或计划进入欧盟市场，本月内梳理清楚三件事——所使用的 GPAI 模型供应商是否签署了 Code of Practice、自身是「提供方」还是「部署方」角色（义务完全不同）、以及 Article 50 要求的 AI 生成内容标识是否已实现。建议由法务和技术共同参与，不要只当作技术问题处理。
