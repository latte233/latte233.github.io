Core Principle

什么是 /goal？它解决了什么问题？

不是更长的 Prompt，而是一套完整的目标生命周期管理系统

terminal — codex CLI 
# 1. 在 ~/.codex/config.toml 中启用 goal 功能

# 2. 设定一个持久化目标

# 3. Codex 开始自主循环执行，直到：

普通 Prompt vs /goal 的根本区别

Architecture

四层架构设计

/goal 由四个核心层面共同构成，缺一不可

01

持久化存储层

目标作为独立状态存储在线程状态数据库中（state-db），与对话历史解耦。/compact 压缩对话不影响目标存在，关闭终端后 codex resume 仍可续接。

02

App-Server API

提供同步、通知和断线重连能力。Server 端维护目标的权威状态，支持多端查询和操作，确保分布式场景下的一致性。

03

Model Tools

Agent 获得专属工具函数（如 goal_achieved），可以看到目标、标记完成和报告阻塞。但权限严格受控——不能随意修改目标本身。

04

Runtime Continuation

核心的自动续跑引擎。每轮结束后 Runtime 检查是否存在 Active Goal，若空闲且无用户输入，自动注入 <goal_context> 启动下一轮。

Runtime Mechanism

Steering Prompt 注入与自动续跑

每一轮 Turn 结束后，Runtime 如何让模型"记住"并推进目标

goal_context — 每轮注入的隐藏上下文 
// Runtime 在每轮 Turn 开始前自动注入
<goal_context>
  <objective>
    将认证模块从 Session 迁移到 OAuth2，确保所有 42 个测试通过
  </objective>

  <status>pursuing</status>

  <budget>
    used_tokens: 145_832
    budget_limit: 500_000
    elapsed_time: "00:23:15"
  </budget>

  <instructions>
    继续推进目标。使用 goal_achieved 工具报告完成，
    需附带客观证据（测试结果、文件变更等）。
    如遇无法自主解决的阻塞，使用 goal_blocked 报告。
  </instructions>
</goal_context>
Step 1 · 目标创建
用户输入 /goal "目标描述"
目标被写入线程的持久化状态数据库，生成唯一 goal_id，状态初始化为 Active。此时目标独立于对话历史存在。
Step 2 · 首轮执行
Runtime 注入 <goal_context>
Runtime 将目标描述、当前状态、已消耗预算等信息打包为 <goal_context> XML，作为隐藏的 System Message 注入到对话最前端，确保模型每轮都能看到目标。
Step 3 · 模型自然停止
一轮 Turn 结束，模型输出 stop
模型完成一轮工作后自然停止（如修改了几个文件、运行了测试）。此时 Runtime 接管决策——检查当前线程是否仍有 Active Goal。
Step 4 · 自动续跑
Hidden Continuation Turn
如果目标仍为 Active、预算未耗尽、无用户排队输入，Runtime 自动启动一个隐藏的 Continuation Turn，注入更新后的 <goal_context>（含最新的 token 消耗、时间等），模型继续推进。
Step 5 · 完成或终止
Agent 调用 goal_achieved / goal_blocked
当 Agent 判断目标达成，调用 goal_achieved 并附带客观证据（测试截图、基准数据）。Runtime 验证后将状态转为 Achieved，自动续跑停止。若预算耗尽则进入 Budget-Limited 状态。
Analysis

优势与局限

任何技术都有适用边界，客观看待 /goal 的能力圈

核心优势

无人值守的长时任务执行
设定目标后可以离开去做别的事，Agent 自主一轮接一轮推进。社区已有连续运行 21 小时的记录。
目标不随上下文压缩丢失
目标独立于对话历史持久化存储，/compact 压缩或终端关闭都不会破坏目标。这是与普通 Prompt 最本质的区别。
基于证据的完成判定
不允许模型"觉得差不多了"就宣称完成，必须提供客观证据（测试通过、文件变更、基准数据），避免"自欺欺人"。
内置 Token 预算管控
可设定 Token 消耗上限。预算耗尽自动进入 Budget-Limited 状态，总结已完成工作和阻塞点，不会无限烧钱。
灵活的生命周期控制
支持 pause/resume/clear 操作，可以随时暂停审查进度、恢复执行或放弃目标。用户始终保有控制权。
Ralph Loop 的官方实现
Greg Brockman 称之为"built-in Ralph Loop++"。将社区自建的循环执行模式内建到 Runtime 层，更稳定、更可控。

已知局限

高昂的 Token 消耗成本
长时运行意味着巨大的 Token 消耗。极端案例中消耗达 9 亿 Token。即使有预算控制，复杂任务的成本仍然可观。
目标漂移（Goal Drift）
长任务中 Agent 可能逐渐偏离原始目标——把目标缩小、将局部进展说成完成、把预算耗尽说成胜利。需要精心撰写可验证的目标来缓解。
不是记忆系统
只保存目标本身和状态信息，不会自动保存每步的中途决策、用户约束、文件修改细节和未完成清单。上下文被压缩后中间过程可能丢失。
不适合简单任务
对于"改个变量名"、"修个 CSS 样式"这类一两轮就能完成的任务，使用 /goal 反而增加不必要的开销和复杂度。
空转风险
当 Agent 陷入困境但未显式报告阻塞时，可能连续多轮空转（无实质 Tool 调用），消耗预算却没有实际进展。虽有空转抑制机制，但仍需警惕。
仅限 CLI 环境
目前 /goal 是 Codex CLI 独有功能，Codex Desktop 不支持。且需手动开启 feature flag，配置门槛存在。

Best Practices

如何写好一个 /goal

强 Goal 需要六大要素，弱 Goal 注定跑偏

明确的结果定义

告诉 Agent "做到什么样"而不是"做什么"。用可度量的指标描述预期结果，如"p95 延迟低于 120ms"而非"优化性能"。

可验证的完成条件

"确保所有 42 个测试通过"比"代码能跑"清晰得多。提供具体的验证命令（如 npm test、benchmark.sh），让 Agent 自行验证。

限定工作范围

"只修改 checkout service 目录下的代码"可以防止 Agent 大范围修改不相关的文件。明确边界减少意外副作用。

设置合理预算

根据任务复杂度预估 Token 消耗量。建议首次使用较低预算试跑，观察实际消耗后再调整。避免不设上限导致费用失控。

用 GOAL.md 代替一句话

复杂目标建议写成独立的 GOAL.md 文件，包含背景、约束、验证步骤等详细信息。然后 /goal 引用该文件，确保目标描述充分且不丢失。

避免模糊表述

避免"优化一下这个项目"、"让代码更好"这类模糊目标。模糊目标 = Agent 自由发挥 = 不可预期的结果 + 浪费的 Token。

强 Goal 示例 vs 弱 Goal 示例 
// ✗ 弱 Goal — 模糊、不可验证、无边界
/goal 优化项目性能

// ✓ 强 Goal — 明确结果、可验证、有边界、有约束
/goal 将 checkout service 的 p95 延迟降低到 120ms 以下，
      由 benchmark/checkout_bench.sh 验证，
      同时保持 tests/ 下所有 correctness 测试全部通过。
      仅修改 src/checkout/ 和 benchmark/ 目录下的文件。

// ✓ 引用 GOAL.md 的方式
/goal 按照 GOAL.md 中的描述完成认证模块的 OAuth2 迁移
When to Use

什么时候该用 /goal

选对场景才能发挥最大价值

场景 推荐方式 原因
大规模代码重构 ✓ /goal 需要跨多文件、多轮持续推进，中间不需要人工干预
性能调优（有基准） ✓ /goal 有明确的数值目标和验证命令，完美匹配证据驱动的完成判定
测试补全 ✓ /goal "覆盖率从 45% 提升到 80%"是可量化目标，适合长时间自主执行
框架/库版本迁移 ✓ /goal 迁移步骤多、涉及文件广，适合设定目标后让 Agent 自主完成
修复一个小 Bug ✗ 普通 Prompt 一两轮就能完成，使用 /goal 增加不必要的开销
探索性开发 ✗ Plan + 交互 需求不明确时不适合设定 /goal，先用 Plan 模式讨论方案
需要频繁确认的任务 ✗ 普通交互 每步都需要人工审核和确认的任务，/goal 的自主执行反而不适用
